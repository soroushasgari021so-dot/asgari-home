# ASGARI HOME — ممیزی نسخه فعلی و نقشه راه اجرایی

تاریخ ممیزی: 2026-11-27  
مبنای بررسی: شاخه `main` مخزن GitHub و پروژه متصل Supabase  
تصمیم محصول: تکمیل و اصلاح نسخه فعلی؛ بازطراحی اساسی فقط در صورت اثبات نیاز فنی

## 1) خلاصه مدیریتی

ASGARI HOME یک اپلیکیشن Flutter فارسی و راست‌چین با هویت مشکی/طلایی است که از Supabase برای احراز هویت، داده‌ها و ذخیره تصاویر استفاده می‌کند. نسخه درج‌شده در `pubspec.yaml` برابر `0.1.3+4` است.

نسخه فعلی از یک نمونه صرفاً نمایشی جلوتر است: فهرست عمومی آگهی‌ها، ورود مدیر، مدیریت آگهی، مدیریت مشتری و پیگیری، فرم درخواست ملک، مدیریت وضعیت درخواست‌ها و چند ابزار محاسباتی در کد دیده می‌شوند. بااین‌حال، داده واقعی آگهی در جدول `public.public_listings` هنگام ممیزی صفر بود؛ بنابراین تجربه عمومی بدون آگهی خالی نمایش داده می‌شود.

## 2) معماری مشاهده‌شده

- اپلیکیشن: Flutter / Dart
- نقطه ورود منبع: `lib/main.dart.txt`
- خط لوله ساخت: GitHub Actions در `.github/workflows/build-apk.yml`
- پایگاه داده و احراز هویت: Supabase
- اتصال برنامه: `supabase_flutter`
- ذخیره تصویر: Storage bucket با نام `property-images`
- پیکربندی اتصال: `SUPABASE_URL` و `SUPABASE_ANON_KEY` از طریق dart-define در CI
- نسخه فعلی: `0.1.3+4`

Workflow فایل `lib/main.dart.txt` را به `lib/main.dart` کپی می‌کند، پروژه Android را تولید می‌کند، اسکریپت `tools/prepare_release.py` را اجرا می‌کند، `flutter analyze` را انجام می‌دهد و APK امضاشده می‌سازد.

## 4) وضعیت واقعی داده در Supabase

جداول عمومی مشاهده‌شده همگی RLS فعال دارند. جداول اصلی:

- `admin_users`
- `public_listings`
- `customers`
- `property_requests`
- `properties`
- `owners`
- `listing_images`
- `visits`
- `transactions`

در زمان ممیزی:
- `public_listings`: صفر ردیف
- `customers`: ۳ ردیف
- `property_requests`: ۵ ردیف
- `admin_users`: یک ردیف
- جداول `owners`, `properties`, `listing_images`, `visits`, `transactions`: صفر ردیف

جداول مالکان، پرونده مستقل ملک، بازدید و معاملات در پایگاه داده وجود دارند؛ اما در مسیرهای کد بررسی‌شده، CRUD فعال و کامل برای آن‌ها مشاهده نشد. بنابراین وجود جدول را نباید با تکمیل قابلیت محصول اشتباه گرفت.

Storage bucket با نام `property-images` عمومی است، محدودیت حجم آن ۱۰ مگابایت و انواع مجاز JPEG، PNG و WebP هستند. سیاست‌های نوشتن/حذف برای مدیران احراز هویت‌شده تعریف شده‌اند.

## 5) یافته‌های ممیزی و اولویت‌ها

### P0 — مانع تجربه قابل‌نمایش
1. **نبود آگهی عمومی:** جدول `public_listings` خالی است. پیش از تبلیغ عمومی، باید چند آگهی واقعی و تأییدشده با رضایت مالک ثبت و نمایش داده شوند. اگر هنوز آگهی واقعی نداریم، صفحه خالی باید به تجربه راهنمایی/ثبت درخواست تبدیل شود و هیچ ملک ساختگی به‌عنوان آگهی واقعی نمایش داده نشود.
2. **تأیید عملیاتی نسخه:** نتیجه اجرای موفق آخرین GitHub Actions در داده‌های قابل‌دسترسی این ممیزی تأیید نشد. باید یک build واقعی، نصب APK و تست روی دستگاه Android انجام شود.

### P1 — امنیت و قابلیت اطمینان
1. **تابع RPC عمومی با SECURITY DEFINER:** تابع `public.increment_listing_view(text)` برای نقش‌های `anon` و `authenticated` قابل اجراست و SECURITY DEFINER است. منطق داخلی آن شناسه UUID را اعتبارسنجی می‌کند، بازدید را برای هر IP محدود می‌کند و فقط آگهی منتشرشده را می‌شمارد؛ بااین‌حال، Supabase Security Advisor برای سطح دسترسی این تابع هشدار داده است. پیش از تغییر باید مسیر فراخوانی و نیاز واقعی به دسترسی عمومی بررسی شود؛ سپس مجوزها/مرز امنیتی اصلاح و با نقش anon و authenticated تست شود.
2. **حفاظت رمز عبور افشاشده غیرفعال است:** قابلیت Leaked Password Protection در Supabase Auth فعال نیست؛ فعال‌سازی آن در تنظیمات Auth توصیه می‌شود.
3. **سیاست‌های RLS تکراری:** Advisor تعداد ۱۵ مورد Multiple Permissive Policies گزارش کرده است. چند جدول از جمله `customers` و `public_listings` سیاست‌های هم‌پوشان دارند. این مورد باید با حفظ رفتار فعلی و تست هر نقش پاک‌سازی شود؛ حذف کورکورانه policy ممنوع.
4. **منبع حقیقت schema در مخزن ناقص/نامنطبق است:** README مسیر `supabase/schema.sql` را معرفی می‌کند، اما این فایل در مسیر اعلام‌شده پیدا نشد. همچنین `pubspec.lock` در مسیر ریشه پیدا نشد. تاریخچه migration در پروژه Supabase وجود دارد، اما فایل‌های متناظر در مسیر متعارف مخزن پیدا نشدند. باید schema و migrationهای قابل‌بازتولید به مخزن اضافه شوند و راه‌اندازی از صفر مستند و آزمایش شود.
5. **مستندات با کد همگام نیست:** README بعضی قابلیت‌ها را «ساخته‌نشده» اعلام می‌کند، درحالی‌که مدیریت آگهی، مدیریت مشتری و پیگیری و مدیریت درخواست در کد دیده می‌شوند. مستندات باید بر اساس نسخه واقعی اصلاح شوند.

### P2 — کیفیت و عملکرد
1. Advisor تعداد ۶ کلید خارجی بدون index مناسب گزارش کرده است؛ indexها باید بر اساس مسیرهای query و حجم داده طراحی شوند.
2. برای جست‌وجو و فیلتر آگهی، pagination و query سمت سرور لازم است تا با رشد آگهی‌ها همه ردیف‌ها یک‌جا دریافت نشوند.
3. مدیریت خطا و پیام‌های کاربری باید از نمایش جزئیات خام خطای سرویس به کاربر نهایی فاصله بگیرد؛ جزئیات فنی فقط در لاگ امن ثبت شود.
4. اطلاعات تماس دفتر در کد ثابت است؛ بهتر است در پیکربندی محیطی/تنظیمات قابل مدیریت قرار گیرد.
5. تست‌های خودکار برای اعتبارسنجی فرم‌ها، محاسبات مالی، وضعیت آگهی و دسترسی نقش‌ها کم است و باید اضافه شود.
