# ASGARI HOME | املاک عسگری

اپلیکیشن Flutter مجموعه املاک عسگری؛ با رابط فارسی و راست‌چین و هویت بصری مشکی و طلایی. این مخزن وضعیت واقعی کد فعلی را مستند می‌کند و نباید قابلیت‌های برنامه‌ریزی‌شده را با امکانات پیاده‌سازی‌شده اشتباه گرفت.

## وضعیت فعلی محصول

### بخش عمومی
- نمایش آگهی‌های منتشرشده از جدول `public_listings`
- جست‌وجو و دسته‌بندی آگهی‌ها
- مشاهده جزئیات و تصاویر ملک
- تماس تلفنی با دفتر و ثبت بازدید آگهی
- فرم ثبت درخواست ملک و ارسال آن به `property_requests`
- ماشین‌حساب تبدیل رهن و اجاره
- ماشین‌حساب مشارکت در ساخت
- پشتیبانی از تم روشن، تاریک و تنظیم سیستم
- نمایش راهنمای راه‌اندازی در صورت نبود تنظیمات Supabase

### بخش مدیریت
- ورود با Supabase Auth و کنترل عضویت مدیر در `admin_users`
- ایجاد، ویرایش، انتشار/عدم انتشار و حذف آگهی
- بارگذاری تصاویر در Storage bucket با نام `property-images`
- مدیریت اطلاعات مشتریان
- ثبت و مشاهده پیگیری‌های مشتریان
- مشاهده درخواست‌های ثبت‌شده کاربران، تغییر وضعیت و بایگانی آن‌ها

### مواردی که هنوز در رابط فعلی محصول کامل نشده‌اند
- پرونده کامل مالک و اتصال ساختاریافته مالک به هر ملک
- مدیریت بازدیدهای حضوری و تقویم بازدید
- ثبت و مدیریت قراردادها و معاملات
- محاسبه کمیسیون و گزارش مالی
- داشبورد تحلیلی و گزارش عملکرد
- جست‌وجوی نقشه‌محور، پیشنهاد هوشمند و قابلیت‌های چندکشوری/چندارزی

وجود جدول‌هایی مانند `owners`، `properties`، `transactions` و `visits` در پایگاه داده به‌تنهایی به معنی تکمیل رابط و گردش‌کار این امکانات نیست.

## ساختار کد

- منبع اصلی Dart در حال حاضر: `lib/main.dart.txt`
- فایل اجرایی `lib/main.dart` توسط GitHub Actions از منبع بالا ساخته می‌شود.
- تنظیمات وابستگی‌ها: `pubspec.yaml`
- Workflow ساخت APK: `.github/workflows/build-apk.yml`
- فایل‌های Android در Workflow تولید می‌شوند؛ بنابراین تغییرات دستی در فایل‌های تولیدی Android باید در Workflow یا اسکریپت آماده‌سازی منعکس شوند.

## متغیرها و GitHub Secrets

در مسیر مخزن GitHub به بخش `Settings → Secrets and variables → Actions` بروید و موارد زیر را تنظیم کنید:

| Secret | کاربرد |
|---|---|
| `SUPABASE_URL` | آدرس پروژه Supabase |
| `SUPABASE_ANON_KEY` | کلید عمومی Publishable/Anon پروژه |
| `ANDROID_KEYSTORE_BASE64` | محتوای فایل keystore به‌صورت Base64 |
| `ANDROID_KEYSTORE_PASSWORD` | رمز keystore و کلید امضای release |

نام alias در Workflow برابر `asgarihome` است. فایل keystore و رمزها نباید در مخزن یا کد برنامه قرار گیرند. هرگز کلید `service_role` یا Secret Key را داخل اپلیکیشن موبایل قرار ندهید.

## ساخت APK

Workflow با Pull Request به `main`، Push به `main` یا اجرای دستی فعال می‌شود. مراحل اصلی:
1. تولید فایل‌های Android
2. بازیابی `lib/main.dart` از `lib/main.dart.txt`
3. تنظیم نام برنامه و مجوز اینترنت
4. امضای release با keystore ذخیره‌شده در GitHub Secrets
5. دریافت وابستگی‌ها و اجرای `tools/prepare_release.py`
6. اجرای `flutter analyze`
7. ساخت APK نسخه release

خروجی در Artifact با نام `asgarihome-updated-release` قرار می‌گیرد. موفقیت ساخت را فقط از وضعیت واقعی GitHub Actions می‌توان تأیید کرد.

## اتصال Supabase و وضعیت مهاجرت‌ها

اپلیکیشن از `supabase_flutter` استفاده می‌کند و آدرس و کلید عمومی را از طریق `--dart-define` دریافت می‌کند. سیاست‌های RLS در پایگاه داده مسئول کنترل دسترسی هستند؛ وجود کلید عمومی در اپلیکیشن به معنی دسترسی آزاد به داده‌ها نیست.

**هشدار مهم درباره همگام‌سازی دیتابیس:** در ممیزی ۲۷ نوامبر ۲۰۲۶، تاریخچه مهاجرت‌های پروژه Supabase شامل مهاجرت‌هایی بود که فایل متناظرشان در مسیر متعارف `supabase/migrations` مخزن پیدا نشد. همچنین فایل `supabase/schema.sql` که در نسخه قبلی این راهنما معرفی شده بود در مخزن موجود نبود. بنابراین:
- از اجرای دستورالعمل قدیمی مبتنی بر `supabase/schema.sql` خودداری کنید.
- مهاجرت‌های موجود در پروژه عملیاتی را حذف یا بازنویسی نکنید.
- پیش از هر تغییر دیتابیس، تاریخچه migration و schema واقعی را با مخزن تطبیق دهید.
- مهاجرت پیشنهادی اصلاح سیاست‌های RLS در Pull Request جداگانه قرار گرفته و تا زمان بازبینی و آزمون، روی پروژه عملیاتی اجرا نشده است.

## وضعیت کیفیت و کارهای باز

- فایل `pubspec.lock` در ریشه مخزن در زمان ممیزی پیدا نشد؛ برای ساخت‌های تکرارپذیر باید lockfile با نسخه Flutter/Dart مورد استفاده CI تولید و commit شود.
- تنظیم Leaked Password Protection در Supabase Auth غیرفعال گزارش شده است و باید از داشبورد Auth بازبینی و فعال شود.
- RPC شمارش بازدید `public.increment_listing_view` عمداً از کلاینت عمومی فراخوانی می‌شود. تابع داخلی شناسه UUID را اعتبارسنجی می‌کند، بازدید تکراری از یک IP را محدود می‌کند و فقط آگهی منتشرشده را می‌شمارد. به همین دلیل هشدار Advisor درباره اجرای عمومی SECURITY DEFINER باید با حفظ قابلیت شمارش بازدید و بازبینی امنیتی مدیریت شود؛ لغو دسترسی بدون جایگزین، قابلیت فعلی را می‌شکند.
- اصلاحات RLS و ایندکس‌های کلید خارجی در PR مستقل پیشنهاد شده‌اند و نیازمند بازبینی و آزمون با نقش‌های anon، کاربر احراز هویت‌شده غیرمدیر و مدیر هستند.

## اصل داده واقعی

در ممیزی فعلی، جدول `public_listings` خالی بود. تا زمان ورود آگهی واقعی با اطلاعات معتبر و رضایت مالک، نباید آگهی نمونه یا ساختگی به‌عنوان فایل واقعی منتشر شود. در محیط خالی، تجربه کاربر باید او را به ثبت درخواست ملک یا تماس با دفتر هدایت کند.
